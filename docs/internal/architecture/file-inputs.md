# File inputs

The `type: file` input: upload, acceptance at creation, claim, delivery to the step, streaming, MCP and retention. `CLAUDE.md` indexes this file. A `§ <Title>` reference names a `###` section in any file of `docs/internal/architecture/`.

### File Inputs
Spec `docs/superpowers/specs/2026-10-29-file-inputs-design.md` (revision 11); guide `docs/src/content/docs/guides/file-inputs.md`; upgrade note `operations/migration-054.md`; terms in `CONTEXT.md` (Input file, Upload, File ID, Safe name, Inputs root, Attachment, Upload URL, File grant). The reverse of artifacts: a person or program uploads a file, the step's script gets a read-only PATH to it.
- **Model**: `type: file` is a primitive — `file_field::FILE_TYPE` is in `template::PRIMITIVE_TYPES` and `RESERVED_TYPE_NAMES`, so a connection type named `file` is rejected by `stroem validate` and shadowed on the server. Allowed in task and action `input`. `stroem validate` rejects `default` / `options` / `multiple` / `secret` / `allow_custom` on it, a file field in an approval action, and an agent task tool whose task has a required file field (`validate_file_field_targets`); it warns when a trigger targets a task with a required file field (same config, no `ref:`). The STORED value (`job.input`, `raw_input`, `job_step.input`, hook payloads, API) is the file ID (`file_` + 32 hex, `file_field::{new_file_id, is_file_id}`); the TEMPLATE value is the path `{root}/{file_id}/{safe_name}` (`file_field::file_path`) — a function of the file, never of the field, so one file has one path in every context of a step and two files never share one. The pure rules live in `stroem_common::file_field`, shared by server, worker and CLI: `safe_name` (basename; every char outside `[A-Za-z0-9._-]` → `_`; a leading `.` / `-` → `_`; ≤ 128 bytes keeping the extension; `None` for empty / `.` / `..`), `JobFiles` (field → `FileRef` under one root: `template_input`, `template_prepared`, `rebase_canonical`, `resolve_target`), `FileInputError { field, kind: CannotUse | Required | InlineTooLarge }` (value-free leaf, no `source`: `Input field 'x': the file cannot be used` / `a file is required` / `inline content is larger than N bytes` — never an ID, name or path), `ClaimedInputFile`.
- **Tables** (migration `054_input_files.sql`, new tables only, no pre-run): `input_file` (one row per upload: `workspace`, `task_name`, `uploaded_by_user_id` — NULL with auth off, `ON DELETE SET NULL` —, `origin` `api | mcp_inline | mcp_url`, `original_name`, `safe_name`, `content_type`, `size_bytes`, `sha256`, `storage_key`, `deleting_at`); `job_input_file` (PK `(job_id, field)`, one row per TASK-level file field, both FKs `RESTRICT`, one file attachable to many jobs); `input_file_upload_token` (SHA-256 of an upload-URL token, `expires_at`, `used_at`). Repos `InputFileRepo`, `JobInputFileRepo`, `UploadTokenRepo` (stroem-db `repos/input_file.rs`). Blob key `{input_files.prefix}{workspace}/{file_id}` (`AppState::input_file_storage_key`), shared by every job that attaches the file. Backend `AppState.input_blob` = `input_files.archive`, else the artifact backend, else the log archive (`main.rs`); none → uploads answer 503 `file storage is not configured`.
- **Upload** (`web/api/input_files.rs::upload_task_file`): `POST /api/workspaces/{ws}/tasks/{name}/files?name=…[&source_job_id=…]`, raw body (no multipart), `DefaultBodyLimit` = `max_file_bytes`, streamed by `input_files::upload::store_upload` → `stream::put_counted` (size + SHA-256 computed while streaming; over the limit → 413, a body or storage error → the fresh key is deleted, nothing kept). Without `source_job_id`: `require_task_run` on the LIVE task, which must declare a file field. With it, `authorise_rerun_upload` follows the execute Re-run order of spec § 4.2: a bad / missing / Deny source answers the one 404 `Source job not found` before ANYTHING else is checked; a pinned source with View → 403 before its ref is resolved; then `check_rerun_source` + same task name (400), `resolve_source_pin` (pinned) or the live task, `require_task_run` + file field. Response 201 `{file_id, name, size_bytes, sha256, content_type, expires_at}`.
- **Acceptance at creation** (spec § 4.4): every call of `create_job_for_task_inner` passes an `input_files::FileGrant`. `Direct { user_id, ttl_secs }` (`FileGrant::direct`) ONLY where a caller starts the job directly — execute, MCP `execute_task`, Re-run, Restart — and only it allows **A1** (own upload: same `(workspace, task)`, `uploaded_by_user_id IS NOT DISTINCT FROM` the caller — an API key or MCP OAuth token resolves to its user, auth off matches NULL —, younger than `upload_ttl_secs`). `TaskChild` for `type: task` dispatch; `Indirect` everywhere else (scheduler and webhook via `trigger_target`, event source, hooks, task retry, agent task-tool children). **A2** (lineage) comes from the creation itself, never from a column of the new row: `CreationMode::Rerun` / `Restart` → the source job, `Retry { failed_job_id }` → the job that JUST failed (not `retry_of_job_id`, the chain's root), `TaskChild` → `parent_job_id`; no uploader or TTL check. `task_file_values` checks shape and `required` on the input AS SUBMITTED (before `merge_defaults`; absent / `null` / `""` = no file) — a required file field with no value fails EVERY creation mode, unlike every other type. `attach_all_tx` writes the rows inside the creation transaction (a retry's: the `link_retry_tx` one) through `JobInputFileRepo::attach_tx`: `FOR SHARE` on the `input_file` row, refuse `deleting_at`, rules lineage then own, first match wins; a refusal is `CannotUse` and rolls the job back. `classify_execute_error` downcasts `FileInputError` right after `InputStorageUnavailable` (before `RenderedRefError` and the `"is not available"` → 500 check) → 400; `agent_task_tool` answers it 400 too. Agent tool schemas leave file fields out (`stroem-agent` `input_schema_to_json_schema`).
- **No storage refuses file-backed creation** (spec § 4.3, revision 10): `JobDefaults.input_storage` comes only from `AppState::job_defaults` (`input_blob.is_some()`), which every production creation path and `Settlement`'s defaults use — a NEW creation path must too; `JobDefaults::from(&ServerConfig)` and `Default` assume `true` (config-only callers, tests). `create_job_for_task_inner` returns the value-free leaf `input_files::InputStorageUnavailable` (`STORAGE_NOT_CONFIGURED`, `file storage is not configured`) for a non-empty `task_file_values` before the transaction — also for an existing attachment that a Re-run / Restart / retry / child replays; `classify_execute_error` downcasts it first → 503, MCP `execute_task` → a tool error with that text. Claim safety net: a runner step of a job with attachments while `input_blob` is `None` fails through `fail_claimed_step` with that text (not withheld).
- **Preflight** (the spec's `trigger_preflight` is `input_files::preflight(schema, input)`): pure; fails on a required file field, else on any file field the input gives a value. Runs after target resolution and BEFORE the concurrency policy in `scheduler.rs` (`Trigger '…' MISSED`, no skipped row, nothing cancelled), in `web/hooks.rs` (400 through `classify_execute_error`, before any job row), and on the single-step hook-action path of `settlement/hooks.rs` (logged to the source job). A `type: task` hook and an event-source emit rely on the creation-time check. A NEW creation path that cannot carry an upload must preflight before its own side effects.
- **ID → path in three places, each from a `JobFiles`, never from the live task schema.** (1) The render context, `render_context::build_entries`, from `Snapshots.files` (`input_files::job_files(load_attachments(job), root)`), never patched into the context afterwards: the job `input` → `JobFiles::template_input` (attached fields); `Scope::ActionBody { prepared_input, action_schema }` → `template_prepared` (file fields of the persisted `action_spec.input`); `each.item` → `rebase_canonical` (a loop item is rendered once in S5 under `/inputs` and moves to the claim root at claim; spec revision 8). (2) The claim's `rendering::merge_missing_action_fields`, which writes `files.path_of(..)` into an unset NON-file action field of the PREPARED input — a value persisted to `job_step.input` (spec § 5.1), which is why a re-claim refreshes it (Claim bullet). (3) `stroem run`, which maps IDs through its own `JobFiles` (`template_input`, `template_prepared`) with no render context. `Snapshots.files` is set by exactly three entries and is NOT best-effort (a file value would render as its ID): `Settlement::advance` (error propagates like a cascade DB error) and `dispatch::init` (→ `[creation] initialisation failed`) under `CANONICAL_INPUTS_ROOT` (`/inputs`), `claim_job` under the claim root. A `file`-typed TARGET (action field, child task field) takes an ID or `{root of this render}/{file_id}/{safe_name}` of a file attached to THIS job (A3, `JobFiles::resolve_target` in `template::render_input_typed_with_files`); anything else is `CannotUse`. An absent optional field stays absent: a missing key is a Tera error, so authors test `when: "{{ input.f | default(value='') }}"` (spec revision 8).
- **Claim** (`claim_job`, spec § 5.2–§ 6.5): `ClaimRequest.inputs_dir` — absolute (else 400 `inputs_dir must be an absolute path`), and its presence means "this worker places input files". Attachments load before any render; a read error is transient and hits every job, so it releases the claim back to `ready` like a transient pin failure (`release_or_fail_claim`, shared with `pin_failure`: no retry attempt, `PIN_RELEASE_RETRY_SECS`, job log `[files] could not load the job's input files, retrying`) and fails the step with `INPUT_FILES_UNREADABLE` only at `MAX_PIN_RELEASES` (spec revision 9). A runner step of a job with files and no `inputs_dir` fails through `fail_claimed_step` with `rendering::OLD_WORKER_INPUTS` (`retry:` applies; never a release — a fleet of old workers would loop). Root: `rendering::inputs_root` — `/inputs` for `type: docker | pod` or `runner: docker | pod`, else `inputs_dir`; agent steps render under `/inputs` and get no files. `ClaimResponse.input_files` = `input_files::claimed_files` — every distinct file of the JOB, once per ID (U9: every runner step gets every file, cross-workspace action steps and every `for_each` instance included). `prepare_step_action_input` → `merge_missing_action_fields(…, files, persisted)` copies a job file into an unset same-named action field by TARGET type: the ID (through A3, `file_target`) into a `file` field, the path into any other. Only when `persisted` (the flow step has no `input:`, so the previous claim's prepared input passes through) is a non-file field holding the same file's path under another root refreshed to the current root (a retried `runner: local` step gets a fresh `inputs_dir`).
- **Delivery**: worker route `GET /worker/jobs/{job_id}/input-files/{file_id}` (`web/worker_api/input_files.rs`: 404 unless attached to that job or when the blob is gone; 503 + `Retry-After: 5` with no storage or a read error). Worker: every claim request carries a fresh `client::fresh_inputs_dir()` = `{temp}/stroem-inputs-{uuid}/in` (`INPUTS_SUBDIR`); for Shell and Docker steps (`needs_worker_download`) `poller::place_input_files` creates the WRAPPER `{temp}/stroem-inputs-{uuid}` with mode `0700` (other host users cannot traverse it, while the visible tree stays readable), then `in/{file_id}/{safe_name}`, streams each file to disk (`download_input_file_with_retry`: a 503 is retried `INPUT_503_ATTEMPTS` × `INPUT_503_DELAY`; size + SHA-256 checked, a mismatch fails the step before the runner starts), then makes files `0444` and dirs `0555` (a Docker step may run as another uid). `InputsDirGuard` owns the wrapper and chmods to `0700` / `0600` before `remove_dir_all`. Docker: `RunInputs.host_dir` bind-mounted `/inputs:ro` in both modes. Pod: `inject_inputs_init` (before the manifest merge — both names are override surface, unvalidated) adds init container `stroem-inputs-init` (`INPUTS_INIT_CONTAINER`, same `init_image` as `workspace-init`) and `emptyDir` `stroem-inputs` (`INPUTS_VOLUME`), read-write there and read-only at `/inputs` in `step`. `INPUTS_INIT_SCRIPT` is a CONSTANT run with `set -eu`; every value comes from env (`STROEM_INPUT_COUNT`, `STROEM_INPUT_{i}_{ID,NAME,URL,SIZE,SHA256}`, `STROEM_INPUTS_ROOT`) and `eval` splices in only the loop counter: `mkdir -p`, `curl -sSf --retry 11 --retry-delay 5` to a file, `wc -c` and `sha256sum` checks, one stderr line naming the file ID per failure. The script is EXECUTED in tests (generated-shell rule): `inputs_script_*` against wiremock on the host from an empty root (size / digest mismatch, 404, 503 retry) and `inputs_script_in_real_curl_image` in `curlimages/curl` (skips without Docker). An init failure surfaces as exit 1 only (TODO.md).
- **Streaming** (spec § 9): no path holds a whole file. Local and S3 `put_stream` / `get_stream` overrides (Local: temp file, fsync, rename; S3: one `S3_PART_BYTES` (8 MiB) part buffer, `PutObject` for a body inside one part, else multipart aborted on any error). S3 multipart declares CRC32 unless the client's `request_checksum_calculation` is `WhenRequired` (`multipart_crc32`, for third-party S3 stores). `stream::download_body` serves both downloads. Bounds are pinned in `tests/log_peak_alloc_test.rs` (50 MiB upload + download, Local and S3, and the MCP `get_input_file` read `read_bounded`, which holds at most its 1 MiB cap) — a new transfer path needs a case there.
- **Job page / redaction**: job detail `input_files[]` (`InputFileRef {field, file_id, name, size_bytes, content_type}`, ordered by field). `walk_job_content` walks it like `steps[]`: `redaction::INPUT_FILE_IDENTIFIER_KEYS` (`field`, `file_id`) stay intact under a secret equal to `file` and under `MaskAll`; `name` / `content_type` are content. UI Re-run prefill and download links read ONLY those two identifiers, never `raw_input` / `input`. User download `GET /api/jobs/{id}/input-files/{field}`: `check_job_acl` on the job row (Deny → 404), `nosniff`, `SAFE_INLINE` else attachment, `filename*=UTF-8''` original name. File CONTENT is never redacted, and the redaction closure is not extended: a file only follows edges along which the job input is already copied (Re-run / Restart `raw_input`, retry `input`, child step input).
- **MCP** (`mcp/tools.rs`): `execute_task` accepts an inline object `{name, content}` or `{name, content_base64}` for a file field (exactly two keys, `decode_inline`; decoded ≤ `mcp_inline_max_bytes`, else `InlineTooLarge`), stored by `store_inline_files` as an `mcp_inline` upload of the caller (`application/octet-stream`) before creation. `create_upload_url {workspace, task_name, file_name}` (Run on the task, file field, safe name) needs `auth.base_url` — a URL is never built from request headers — and file storage (else the tool error `file storage is not configured`, no token minted), and returns `{upload_url: {base_url}/api/uploads/{token}, method, max_bytes, expires_at}`; the token is 32 random bytes stored as SHA-256. `POST /api/uploads/{token}` (`upload_by_token`) is on the PUBLIC router (no `require_auth`, the token is the credential): `UploadTokenRepo::consume` uses the token up BEFORE the body is read (a failed upload needs a new URL), then re-checks at upload time that the token's user still exists, still has `Run` on the task (`tasks::task_permission_for_user`) and that the task still has a `file` field; unknown / used / expired / any failed re-check → one identical 404 `Upload URL not found`; stored as `mcp_url`, owned by the token's user. The token is a credential: the request span records the path as `/api/uploads/{token}` (`web::span_uri`, the `TraceLayer`'s `make_span_with`).
- **Retention** (spec § 4.7): `JobRepo::delete` deletes the job's `job_input_file` rows first, in one transaction with the job row — never a blob. `recovery::sweep_input_files`, at the end of `retention_cleanup` (leader-gated, every `retention.interval_secs`, with or without `retention.job_days` / `worker_hours`): deletes expired upload tokens, then — only with an `input_blob` — up to 1000 `InputFileRepo::sweep_candidates` (unattached and older than `upload_ttl_secs`, or already marked), one recovery heartbeat each: (1) `mark_deleting_tx` — `SELECT … FOR UPDATE` on the row, THEN a separate `EXISTS` on `job_input_file` (a fresh READ COMMITTED snapshot taken after the lock), only then `deleting_at`; a single `UPDATE … WHERE NOT EXISTS` would miss an attachment committed while it waited; (2) delete the blob (a failure keeps the marked row for the next sweep); (3) `InputFileRepo::delete`. A creation blocked on its `FOR SHARE` then sees `deleting_at` and fails `CannotUse`. Tests: stroem-db `sweep_vs_creation_{creation,sweep}_first`.
- **Config / metrics**: `input_files:` (`InputFilesConfig`: `max_file_bytes` 100 MiB, `upload_ttl_secs` 86 400, `upload_url_ttl_secs` 900, `mcp_inline_max_bytes` 1 MiB and ≤ `MAX_MCP_INLINE_BYTES` (1 468 006, so its base64 fits the 2 MiB `/mcp` body limit), `prefix` `inputs/`, optional `archive`; every cap > 0 in `ServerConfig::validate`, and at most `MAX_UPLOAD_TTL_SECS` (30 days), `MAX_UPLOAD_URL_TTL_SECS` (24 h) and `MAX_INPUT_FILE_BYTES` (`S3_MAX_PARTS` 10 000 × `S3_PART_BYTES`) — larger values overflow the expiry arithmetic, wrap the sweep's signed age, or exceed one S3 multipart upload; env `STROEM__INPUT_FILES__…`). Counters `stroem_input_file_uploads_total{origin, result}` (`ok | too_large | invalid_name | error`) and `stroem_input_file_bytes_total{origin}` (stored bytes of successful uploads), both recorded in `store_upload`.
- **CLI**: `stroem-api trigger --file FIELD=PATH` (repeatable, `remote/trigger.rs`) streams each upload, then executes with the IDs; a non-object `--input` or a key in both `--input` and `--file` is an error before any upload. `stroem run` takes the local path as the field's value in `--input` JSON and copies it read-only to `{temp}/stroem-run-inputs-{uuid}/{local file id}/{safe_name}` (`local/run.rs::stage_file_inputs`), so paths keep the server's shape; still local scripts only. A local CLI error may name the user's own path: the no-value rule is for server messages.
- **`stroem run` staging is private**: `create_private_dir` creates the root `{temp}/stroem-run-inputs-{uuid}` atomically with mode `0700` (never an existing dir), like the worker's wrapper, because the tree below it is world-readable (`0555` / `0444`); `InputsRoot` relaxes dirs to `0700`, never wider, before removal (test `staged_inputs_root_is_private_and_removed`).
- **Rollout**: every server replica, then every worker, then YAML with `type: file` — an old server reads `type: file` as a connection type (400), an old worker gets `OLD_WORKER_INPUTS`. Tests: stroem-server `input_file_{upload,creation,claim,retention}_test.rs` + `s3_integration_test.rs`, stroem-db `input_file_test.rs`, stroem-cli `run_file_inputs.rs`, stroem-runner `inputs_*`.
