# Testing and CI

Test layout and the shared Postgres container, CodeQL setup, and the release pipeline. `AGENTS.md` indexes this file. A `§ <Title>` reference names a `###` section in any file of `docs/internal/architecture/`.

### Tests

- **Tests**: Unit tests in-module (`#[cfg(test)] mod tests`). Integration tests in `tests/` dirs using `testcontainers` for Postgres. **One integration-test binary per crate**: `tests/main.rs` (target `integration`, `autotests = false`) declares every test file as a `mod`, and shared fixtures are `crate::common::…`. A new test file is a `mod` line in `tests/main.rs`, never a new target — an undeclared file is silently never compiled, which `stroem-common/tests/test_targets_guard.rs` fails on. One file or test: `cargo test -p stroem-server --test integration git_refs_claim_test::`. Sole exception (the guard's `OWN_BINARY` allow-list): `stroem-server/tests/log_peak_alloc_test.rs` (`harness = false`; its counting global allocator would count every other test). A crate's integration tests share one process, so process-global state is shared across files: the global metrics recorder counts every test's jobs (an exact metric count needs a recorder local to the test, `metrics::set_default_local_recorder`), and `#[serial]` without a key serializes `ha_test` and `metrics_test` together. All DB-backed tests get their pool/URL via `stroem-test-support::{test_pool, test_db}` — one Postgres container per test *binary*, so one per crate (via a per-process `OnceCell`), never per test. The binary removes its container (and data volume) as it exits, passed or failed — a libc `atexit` handler, since a `static` is never dropped; only a crashed or interrupted run (Ctrl-C, `kill -9`) leaves one, labelled `stroem.test=true` for `scripts/test-clean.sh`. Each is named after its binary, `{package}-{target}-{pid}-{nonce}` (e.g. `stroem-server-integration-48213-9f3a1c`; `unit` for a lib's own tests) — `stroem_test_support::container_name`. Never call `testcontainers` directly in a new test file. The `stroem-server` / `stroem-worker` bins have no tests (`test = false`). **Parallel worktrees share one cargo target dir** and the crates have the same names in every worktree, so `cargo test` in one worktree can run a test binary another worktree just built ("0 tests matched", failures of code that is not on your branch; seen 2026-10-30). Build one worktree at a time, and before trusting a full run after parallel builds, `cargo clean -p` every workspace crate first.

### CodeQL

- **CodeQL**: advanced setup (`.github/workflows/codeql.yml`), not GitHub's default setup — default setup cannot exclude paths. `.github/codeql/codeql-config.yml` `paths-ignore`s test code (`crates/*/tests`, `crates/*/examples`, `crates/stroem-test-support`, `**/tests.rs`, `test_support.rs`, UI tests), because CodeQL flags fixture secrets and assertion messages and re-flags them at new line numbers after every edit (`validation.rs` alone produced 126 of the 183 alerts raised by 2026-10-17). A unit-test module whose fixtures carry secrets or passwords, or that prints validation output, lives in a sibling `tests.rs` (`#[cfg(test)] mod tests;` → `src/<module>/tests.rs`), never inline. Analysis categories must stay `/language:<language>`: another category orphans every existing alert and opens duplicates.

### Release Pipeline
- `.github/workflows/release.yml` (tags `v*`), linux only (no darwin/windows): `build-binaries` is a two-leg matrix — `linux-amd64` on `ubuntu-latest`, `linux-arm64` on GitHub's hosted `ubuntu-24.04-arm` — each a NATIVE build inside `container: rust:1-bookworm` (glibc 2.36 baseline; no `cross`, no QEMU-emulated rustc, no `--target`, output in `target/release`). Each leg builds the UI, then all four binaries (`stroem-server`, `stroem-worker`, `stroem`, `stroem-api`), and uploads `binaries-<name>` with four `<bin>-<target>.tar.gz` tarballs (`x86_64-unknown-linux-gnu` / `aarch64-unknown-linux-gnu`). The upload `path:` needs both globs `stroem-*-<target>.tar.gz` and `stroem-<target>.tar.gz` — the first alone misses the `stroem` CLI tarball.
- Three multi-arch (`linux/amd64,linux/arm64`) Docker images published to `ghcr.io/{owner}/stroem-{server,worker,runner}`, tagged `{version}`/`{major.minor}`/`{major}` via `docker/metadata-action`. The image jobs use QEMU (`docker/setup-qemu-action`) for the arm64 platform; their RUN layers only `apt-get` and download tools, never compile. `build.yml` (push to `main`: `latest`, `sha-*`) compiles Rust inside Docker and is still `linux/amd64` only. The release jobs' `metadata-action` keeps its default `latest=auto`, so a stable release also moves `latest` to its multi-arch image until the next `main` build replaces it with an amd64-only one (`build.yml` skips the tagged release commit itself).
- Helm chart (`helm/stroem`) version/appVersion stamped from the tag and pushed to `oci://ghcr.io/{owner}/charts`.
- Final `release` job collects all binary artifacts and creates the GitHub Release with auto-generated notes.
- Release Dockerfiles (`docker/Dockerfile.server.release`, `docker/Dockerfile.worker.release`) COPY the pre-built binary of the build platform in (`dist/<bin>-linux-${TARGETARCH}`, prepared by the image job from both tarballs); `Dockerfile.runner` has no Strøm binary. All three pick tool downloads by `dpkg --print-architecture`.
