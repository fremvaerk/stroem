# Operations

Metrics, database rules, health probes, log storage and streaming, worker recovery and high availability. `AGENTS.md` indexes this file. A `§ <Title>` reference names a `###` section in any file of `docs/internal/architecture/`.

### Prometheus Metrics
- `crates/stroem-server/src/metrics.rs` — recorder install + `gather_gauges` + metric name constants (`STROEM_*`) + RED tower middleware (`track_http_metrics`)
- `crates/stroem-server/src/web/metrics.rs` — `GET /metrics` handler
- Always enabled. Optional config: `metrics: { public: bool }` (default `false` → requires `worker_token` Bearer, same auth posture as `/healthz/detail`).
- Hybrid recording: counters/histograms inline at event sites via `metrics::counter!` / `metrics::histogram!`; gauges sampled at scrape time in `gather_gauges` (2s timeout per DB query via `tokio::time::timeout`, errors logged + skipped, NOT zeroed — Prometheus treats absence as stale).
- DB queries inside `gather_gauges` run concurrently via `tokio::join!` so worst-case scrape latency is bounded at 2s, not 6s.
- RED middleware applied to `/api/*` only. `/worker`, `/hooks`, `/mcp` deliberately excluded (worker traffic would swamp user-facing signal).
- Job-completion counter is incremented inside `settlement::terminal::claim` — see § Settlement.
- Global `replica_id` label added at recorder install — keeps multi-replica scrapes from collapsing into one series.
- Helm: `serviceMonitor.enabled: true` renders `templates/servicemonitor.yaml`; uses `bearerTokenSecret` when `metrics.public: false`.
- New metrics: add a `pub const` in `metrics.rs`, add the recording site, add an integration test in `crates/stroem-server/tests/metrics_test.rs`, document in `docs/src/content/docs/operations/metrics.md`.

### Database queries (sqlx)

- **Database**: sqlx with runtime queries (`sqlx::query()` / `sqlx::query_as()`), NOT compile-time macros. sqlx 0.9's `query*()` / `raw_sql()` take `impl SqlSafeStr`: a `&'static str`, or `AssertSqlSafe(String)`. A query that only splices in a constant column list uses the repo's `job_columns!()`-style macros with `concat!` (stays `&'static str`); `AssertSqlSafe` is only for SQL whose SHAPE varies (optional filters, ACL `IN` lists, batch `VALUES`) and is built from constant fragments and `$n` placeholders, with a one-line `// AssertSqlSafe: …` comment saying why. Values always go through `.bind()`, never into the string.

### Database
- Runtime sqlx queries, NOT compile-time checked. Migrations in `crates/stroem-db/migrations/`
- Migration 050 builds its indexes inside the migration transaction; its header documents the manual `CONCURRENTLY` pre-run (migration 009 precedent; user-facing copy in `operations/migration-049-050.md`). Index changes that scan a large table go in their own migration under NEW names with `IF NOT EXISTS`, so the pre-run and the migration never collide. Same rule for a widened CHECK: 051 adds it `NOT VALID` only when the check does not already accept `'deferred'` (a `DO` block on `pg_get_constraintdef`), and 052 `VALIDATE`s it; 051's header documents the manual pre-run (widen + `VALIDATE`), after which both are no-ops (`operations/migration-051-052.md`, stroem-db `migration_test::test_051_052_templated_refs_schema`). 053 follows the same rule: two partial indexes on `job` for the trigger last-run lookup, manual `CONCURRENTLY` pre-run in its header, `operations/migration-053.md`, test `migration_test::test_053_trigger_run_indexes`.
- Job claiming: `SELECT ... FOR UPDATE SKIP LOCKED`
- `job.revision` stores workspace revision at creation. Sub-jobs and hook jobs inherit parent's revision — except a cross-workspace child (task owner's current revision) and a child with its own pin (`task_revision`); a pinned job's `revision` is its commit (`git_ref` set, § Git refs).

### Health Check
- Three endpoints, split by question. `GET /livez` (unauthenticated, Helm LIVENESS): should this process be restarted? — background loops only, NO DB check (a restart does not fix a DB outage); body `{"status": "ok" | "stalled" | "stopped"}`, no task name. `GET /healthz` (unauthenticated, Helm READINESS): can this replica serve traffic? — DB only, unchanged. `GET /healthz/detail` (worker token): leader flag + per-task `ok | stalled | stopped | follower`. A hung scheduler must restart the pod, not pull a replica that still serves API/worker traffic out of the Service — never merge the two probes.
- Two signals per loop in `BackgroundTasks`: `AliveGuard` flags (`*_alive` — catches an EXITED task) and `Heartbeat`s (`*_beat` — catches a HUNG one; prod 2026-09-16 the scheduler sat silent for 9 h with its guard held). `Heartbeat` uses a process-local MONOTONIC clock (wall-clock corrections must neither fake nor hide a stall). Pure policy: `web/health.rs::task_health(alive, beat_age, stall_after)` → `Ok | Stopped | Stalled`.
- Failure rules: `Stalled` fails `/livez` and `/healthz/detail` on ANY replica (followers run the loops too). `Stopped` fails `/livez` on ANY replica too, but only if the loop ever beat — a never-started task (router-only tests, the window before `main` spawns it) must not fail the probe; `/healthz/detail` reports `"stopped"` (503) on the leader or for a loop that ever beat, and `"follower"` only for a never-started loop on a follower. Before spec 2026-10-20 § 4.4.1 a follower's exited loop passed `/livez`; with self-release such a replica never becomes leader again, so only a restart repairs it. A shutdown makes the loops exit (`stopped` on every replica for those seconds); the kubelet stops liveness probes of a pod with a deletion timestamp.
- **Beat = progress, not iteration.** Each loop beats at the top of its iteration, once per unit of work inside it, AND once more after the work before it sleeps (so the sleep is never charged to a unit that finished just inside its budget) (per fired trigger, per recovered step, per retention job, per collected/reconciled event source and per cancelled consumer job), so a long batch of bounded units does not read as a stall. Thresholds bound ONE unit: scheduler 300 s, event source 600 s, recovery `max(1800, 5 × sweep_interval_secs)`. The scheduler never sleeps longer than `scheduler::MAX_SLEEP` (30 s). A NEW background loop needs a guard, beats at both levels, and a row in `health::background_report`. Known gap: a single unit with an unbounded external call (`force_refresh` git reload, `vals`, or a scheduler fire whose `ref:` target resolves cold — ls-remote + fetch + `ensure`, each up to `load_timeout`, behind a resolve lock with no acquire timeout) can still outlast its threshold — see TODO.md. The workspace watcher is not one of these three loops and has its own deadline/backoff/observability path instead (`LoadBudget`, `stroem_workspace_load_overdue`, see § Multi-Workspace's workspace-refresh bullet); external reloads (API/peer/`force_refresh`) still take no load permit and have no watchdog (spec § 4.10, TODO.md).
- Gauge `stroem_background_task_last_tick_age_seconds{task}` (absent before the first beat). Tests: `health::tests::test_task_health_*`, `ha_test::livez_*`, `metrics_test::background_task_last_tick_age_reflects_heartbeat`.

### Log Storage
- `LogStorage` — local JSONL for live buffering + optional `LogArchive` backend (S3 or local)
- Archive keys: `{prefix}{workspace}/{task}/YYYY/MM/DD/YYYY-MM-DDTHH-MM-SS_{job_id}.jsonl.gz` (gzipped)
- Upload spawned after hooks fire (includes server events).
- **Reads are bounded** (spec `docs/superpowers/specs/2026-09-22-log-tail-streaming-design.md`): `LogStorage::read_tail` (default 256 KiB, whole lines, `truncated`/`total_bytes`) and `LogStorage::stream_full` (NDJSON stream) are the ONLY readers; the String-returning `get_log`/`get_step_log` were removed on purpose — never add a reader that materialises a whole log. Primitives live in `crate::log_read` (`matcher`, `splitter`, `local`, `archive`). Finished jobs: tail = union of local + archive tails; full = in-memory union under `log_storage.read.merge_max_{bytes,lines}`, else local-first single source. `X-Stroem-Log-Source` names the source. Bounds are enforced by `tests/log_peak_alloc_test.rs` (counting allocator, `harness = false`) — a new read path needs a case there. Read fallback: `.jsonl` → legacy `.log` → (terminal) archive; `NotFound` is never a 500.
- Config: `archive` (preferred) or `s3` (legacy) in `log_storage` section.
- **Server events**: `append_server_log()` writes `step: "_server"` entries for hook failures, orchestration errors, recovery timeouts.
- Worker pushes log lines in requests of at most 1 MiB (`stroem-worker` `client.rs::LOG_PUSH_MAX_BYTES`); `/worker/jobs/{id}/logs` keeps axum's default 2 MiB body limit — a single batch per flush used to 413 and lose the lines.

### WebSocket Log Streaming
- `GET /api/jobs/{id}/logs/stream` — backfill = the default tail (`read_tail`), then live via `tokio::sync::broadcast`
- Subscribe BEFORE reading the backfill (`ws.rs::subscribe_then_backfill`): `LogBroadcast::broadcast` drops a chunk nobody is subscribed to, so read-then-subscribe lost every chunk pushed in between (CI flake on v0.16.6, widened by `read_tail` pinning the file length at open). This closes the read-to-subscribe gap at the price of a possible duplicate; lag past `CHANNEL_CAPACITY` (256 chunks) and signal-only HA chunks can still skip frames. `forward` OWNS the receiver so every exit drops it before `remove_channel` — calling `remove_channel` with the handler's own receiver alive made the no-receivers check always fail and leaked every viewed job's channel allocation (Tokio frees the queued values when the last receiver drops). The UI does not use this endpoint (its last caller, `use-job-logs.ts`, was deleted as dead code in 89ec614); it serves external clients.

### Worker Recovery
- `recovery.rs` — sweeper phases: (1) stale workers → fail steps, (2) timed-out steps, (2.5) timed-out suspended steps, (3) timed-out jobs, (4) unmatched ready steps, (4.5) `readvance_stalled_pinned_jobs` — `advance` every `running` pinned job with no `ready`/`claimed`/`running`/`suspended` step, and every such `pending` one that has at least one terminal step that is not `carried_over` (`JobRepo::get_stalled_pinned_jobs`; a restart's carried rows are terminal from creation on; a step that fails at claim — release cap, permanent pin or render error — or whose tarball download is exhausted leaves a never-started job `pending`; a `pending` job with no terminal step is left to its creation-time init — a heuristic that narrows, not excludes, an overlap with init: a root step failing at claim, or an init dispatch failure, can still make a job listable mid-init, the same race class as that failure's own `advance`), one heartbeat per job, so a job whose `advance` hit a transient pin error does not strand; a PERMANENT pin error there fails the job (§ Git refs). Phase 4.5 is bounded per sweep (`recovery::StalledSweepBounds`: at most 50 jobs, no new `advance` after 60 s — the first always runs), resumes from `AppState::stalled_pinned_cursor` (moved only past ADVANCED jobs; the listing orders by `job_id` after the cursor and wraps), and skips, for the rest of the sweep, the other jobs of a pin just seen unavailable (job still non-terminal and its commit not in the PinStore after `advance`) — a git outage with many cold pins must not hold up the next sweep's stale-worker and timeout phases. Each attempt logs one `[pin] … not available yet` line; a failed listing query is logged and the sweep continues (retention still runs). Test: `stalled_pinned_sweep_is_bounded_and_resumes_on_the_next_tick`. (4.6) `readvance_deferred_steps` — `advance` every non-terminal job with a deferred `ready` step older than `unmatched_step_timeout_secs` and no live resolution lease (bounded and resumable like 4.5, cursor `AppState::deferred_steps_cursor`).
- Stale-worker and step-timeout failures pass the observed claim identity (`StaleStepInfo::claim()` → `Settlement::claimed_step_failed`, `expected = [Running]` + `expected_claim`) so a released and reclaimed — or completed — step is not failed on the previous attempt.
- `pin_eviction_once` runs on every tick on EVERY replica, before the leader gate: the PinStore is replica-local.
- Config: `heartbeat_timeout_secs` (120), `sweep_interval_secs` (60), `unmatched_step_timeout_secs` (30)
- Data retention: optional `retention` section with `worker_hours`, `job_days`. `job_days` counts from `completed_at` (falling back to `created_at`), never creation alone: a long-running job swept the moment it turned terminal lost its hooks/task retry to the `source_job_id` / `retry_of_job_id` FK (`JobRepo::get_old_terminal_jobs`, test `test_retention_counts_from_completion_not_creation`).
- Strategy: fail, don't retry — avoids non-idempotent side effects
- A `fail_or_retry` DB error for one step is logged to that job and the sweep continues with the next step; before the settlement module it aborted the tick.
- HA: gated on `state.leader.is_leader()`. Followers run the loop but skip sweeps.

### High Availability (multi-replica server)
- **Leader election**: `leader.rs` — one server replica holds a Postgres advisory lock (`pg_try_advisory_lock(0x5354524D4C445201)` = "STRMLDR" + version byte). Lock is held on a dedicated `PgConnection`, released automatically when the session ends (pod restart, network partition, DB restart). `AppState.leader.is_leader()` is checked at the top of `scheduler.rs`, `event_source.rs`, `recovery.rs` ticks. Default for tests/single-replica: `LeaderElection::always()`.
- **Leader lease / validity / self-release** (spec `docs/superpowers/specs/2026-10-20-leader-stale-lock-design.md`; prod 2026-10-19: a frozen node's kernel kept the leader session alive, no leader for 16.5 h). `try_acquire` sets `idle_session_timeout` (the **lease**, 30 s) with `set_config(.., false)` BEFORE `pg_try_advisory_lock`; PostgreSQL < 14 (SQLSTATE `42704`) → `LeaseStatus::Unsupported`, one WARN, no lease. **From the lock query on, the leader session sends only simple-protocol queries (`sqlx::raw_sql`, constant SQL)** — an extended-protocol exchange cut before its Sync leaves the backend waiting with NO idle timer armed (timers arm only at ReadyForQuery); never add a `sqlx::query` on the lock-holding connection. `is_leader()` = monotonic now < `valid_until_ms` = (send time of the last successful ping or lock query) + **validity** (20 s); ping bounded by `ping_timeout` (5 s), a whole acquire by `acquire_timeout` (10 s); a ping error/timeout drops the connection. **Config** `leader: { lease_secs: 30, self_release_after_secs: 30 }` (`config::LeaderConfig`, lease 10–3600, release 0 = off or 1–3600, env `STROEM__LEADER__LEASE_SECS`); `LeaderConfig::timing()` → `LeaderTiming::from_lease` derives retry = ping = min(L/6, 5 s), acquire = min(L/3, 10 s), validity = floor(2L/3) in integer ms — the caps keep follower attempts, broken-connection detection and the early-end overlap bounded for a long lease (spec revision 8; revision 7 removed them and the user restored them) — never add another independent knob. `check()` = spec § 4.1 invariants: `ServerConfig::validate` runs it (release builds have no debug asserts), `start_with` debug-asserts it (tests use sub-second values). **Self-release**: `main` installs `web::health::leader_fitness_probe` via `set_fitness_probe`; when a gated loop is unfit — `Stalled`, or `Stopped` after its first beat (`health::unfit_loop`, the `/livez` rules) — for `release_after` (30 s) the leader drops the lock and does not try to acquire while that lasts (`next_action`). `release_after = None` (config 0): `observe_fitness` never calls the probe — no release, no acquire suppression; the health rules stay. `run_loop` starts no iteration once `cancel` fired (shutdown makes the loops `Stopped`). The scheduler beats once before its initial `load_triggers`. Followers log the holder (`lock_holder`: `pg_locks` ⨝ `pg_stat_activity`, filtered by database) at INFO on change / every 15 min and WARN when it is idle past the lease or not `stroem-leader`. Residuals (accepted, spec § 5.2): overlap ≤ `2 × ping_timeout + retry_interval` = min(L/2, 15 s), never more than the validity, after an EARLY session end; in-flight gated work (one sweep, one reconcile, a scheduler batch) runs on after a handover; no write-level fencing. Test hooks: `pause_for_test`, `apply_lease` with any parameter name. Integration tests `ha_test::lease::*` use a message-framing TCP proxy (freeze / delay / cut a `Q`, with barriers) — the shared test image is `postgres:15-alpine` because the lease needs PostgreSQL ≥ 14.
- **Cross-replica event bus**: `events.rs` — Postgres `LISTEN/NOTIFY` over `sqlx::postgres::PgListener`. Three channels: `stroem_job_cancelled` (job cancel → all replicas' `cancelled_jobs` cache), `stroem_workspace_reloaded` (revision change → peers re-read workspace cache), `stroem_job_log_chunk` (worker log push → peer WS subscribers). Payloads carry the originating replica's UUID; listeners drop self-emitted messages to avoid duplicate broadcasts.
- **Publishers** (one-line each, all best-effort, DB is source of truth):
  - `cancellation.rs` cancel_job — publishes `stroem_job_cancelled` after local insert.
  - `web/worker_api/jobs.rs` append_log — publishes `stroem_job_log_chunk` after local broadcast. Lines > `NOTIFY_MAX_BYTES` (3500) degrade to signal-only.
  - `workspace/mod.rs` watcher — publishes `stroem_workspace_reloaded` when source revision changes. `start_watchers(cancel, Some(event_bus))` opts in.
- **`/healthz`**: `web/health.rs` — leader-aware. Process + DB checks always required. Scheduler/recovery/event_source liveness only failure-eligible on the leader; followers report `"follower"` and return 200. Adds `checks.leader: bool`.
- **Replica id**: generated per-process (UUID v4) in `main.rs`, passed into `EventBus::new` for self-filtering.
- **Config**: `config::log_ha_diagnostics()` logs SHA-256 fingerprints of `auth.jwt_secret` + `auth.refresh_secret` at startup so operators can verify both pods loaded the same value.
- **Helm**: defaults at `server.replicas: 2`, `RollingUpdate` with `maxUnavailable: 0`, `terminationGracePeriodSeconds: 60`, `preStop sleep 10`, PodDisruptionBudget `minAvailable: 1`, topologySpreadConstraints by hostname. See `docs/src/content/docs/operations/high-availability.md`.
- Integration tests: `crates/stroem-server/tests/ha_test.rs` (leader uniqueness, failover, lease / validity / self-release in `mod lease`, NOTIFY roundtrip per channel, oversize fallback, self-filter).
