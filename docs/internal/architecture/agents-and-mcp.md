# Agents and MCP

The MCP server and its tools, and `type: agent` LLM steps. `CLAUDE.md` indexes this file. A `§ <Title>` reference names a `###` section in any file of `docs/internal/architecture/`.

### MCP Server (Model Context Protocol)
- Feature-gated: `mcp` cargo feature (enabled by default). Config: `mcp: { enabled: true }` (disabled by default)
- Endpoint: `/mcp` via Streamable HTTP. Crate: `rmcp` with `#[tool_router]` / `#[tool]` macros
- 22 tools: `list_workspaces`, `list_tasks`, `get_task`, `execute_task`, `create_upload_url`, `get_job_status`, `get_job_logs`, `list_triggers`, `list_attention_triggers`, `refresh_workspace`, `get_task_stats`, `get_stats`, `list_workers`, `get_worker`, `get_input_file`, `list_jobs`, `cancel_job`, `restart_job`, `rerun_job`, `approve_step`, `list_artifacts`, `get_artifact`. File inputs (inline objects in `execute_task`, `create_upload_url`): § File Inputs.
- **Job actions share their REST body** (§ Job Lineage → Shared job actions): `restart_job`, `rerun_job` and `approve_step` call `web::api::{restart, rerun, approve}` with a `web::api::caller::Caller` built from the MCP claims, and map the returned `AppError` with `mcp::tools::app_error` (400 / 409 / 413 → invalid params; 401 / 403 / 404 / 503 → the tools' usual `internal_error` with the fixed message; 500 → logged, fixed `Internal server error`). Never re-implement one of these flows in a tool. `rerun_job` takes the source's own task (`Destination::Source`) and replays every schema field `input` does not set (`Replay::Unset`). `approve_step` keeps an absent `input` absent (`approval_input`): `{}` would run the required-field check and add `"input": {}` to the step output.
- **Read tools run the REST handler's code** (every read tool except the older `list_workspaces`, `list_tasks`, `get_task`, `get_job_logs`, `list_artifacts`, `get_artifact`, which keep their own code and shapes, TODO.md): a tool calls the same `pub(crate)` function as its REST route, with the same caller and error mapping as the job actions: the function takes a `web::api::caller::Caller` (REST passes `Caller::of(&auth_user)`, MCP `tools.rs::caller`, whose `claims.is_admin` is the DB-derived value), and the tool maps its `AppError` with `app_error` (REST message; `Internal` → `Internal server error`, cause logged). `list_triggers` / `list_attention_triggers` = `web/api/triggers.rs::{workspace_triggers, attention_triggers}`. `refresh_workspace` = `web/api/workspaces.rs::refresh` (shared 5 s cooldown; `TooManyRequests` → its message). `get_task_stats` = `web/api/tasks.rs::task_stats`, `get_stats` = `web/api/jobs.rs::dashboard_stats`. `list_workers` / `get_worker` = `web/api/workers.rs::{worker_list, worker_detail}` (no ACL on the list, as in REST; the detail filters steps by ACL and redacts each row with one `RedactionMemo`). `get_input_file` = `web/api/input_files.rs::job_input_file` (the REST lookup and ACL), then the `get_artifact` limits: the row's `size_bytes` over 1 MiB is refused with the relative URL before any read, else `input_files::stream::read_bounded` (stops past the cap whatever the blob's size; pinned in `tests/log_peak_alloc_test.rs`). `list_jobs` = `web/api/jobs.rs::job_list` (ACL scope in SQL before `LIMIT`; MCP keeps its `count`/`jobs` keys and its default 20 / max 100, and adds `total`). `get_job_status` = `web/api/jobs.rs::job_detail` (the whole REST job detail and its redaction), then `cap_job_detail` and a compact answer: over `MCP_JOB_DETAIL_MAX_BYTES` (256 KiB) the largest content values are replaced with a note, listed in `truncated_values` — never before redaction. A new read tool extracts its handler body the same way; never hand-write a `json!` of job content in `tools.rs`.
- Auth: Bearer token (API key or JWT) via `tokio::task_local!`. Per-tool ACL checks.
- **Admin mirrors the user (re-derived per request)**: MCP grants admins the same ACL bypass they have in the UI/REST API, but admin is NEVER carried in the OAuth access token. The token is minted with `is_admin: false` (`oauth/token.rs`, defense in depth); `mcp/auth.rs::authenticate` re-reads the user's live `is_admin` from the DB on every request (OAuth path) — matching the API-key path, which also reads it fresh. This means revoking admin takes effect **immediately** (no access-token-TTL lag). Do NOT reintroduce `is_admin` into the minted token; `load_user_acl_context` trusts `claims.is_admin`, and the MCP auth layer is the single place that sets it from the DB.
- **Host allow-list**: rmcp's Streamable-HTTP transport enforces a DNS-rebinding `Host` allow-list (loopback-only by default — would reject all proxy traffic *after* auth passes). `build_mcp_routes` calls `resolve_allowed_hosts()` to allow loopback + the `auth.base_url` host + optional `mcp.allowed_hosts`. `mcp.allowed_origins` (default empty = Origin check off) for browser clients. Middleware order: auth runs outer, rmcp transport (host check) inner — so tokenless probes get 401 while a *valid-token* request to a non-allowed host hits the transport-level Host rejection.

### Agent Actions (type: agent — LLM Calls)
- Worker-side dispatch. Workers need `"agent"` tag and `agents:` config with LLM provider API keys.
- 19 providers via `rig-core` (0.43; crate path `rig_core`, features `reqwest` + `rustls`). `prompt` and `system_prompt` are Tera templates. `provider::build_model` maps each `type` to a rig client: `openai` is pinned to Chat Completions (`OpenAI::chat`, not rig's Responses default); the OpenAI-compatible vendors use rig's `openai::wire` dialects; `galadriel` (dropped upstream) is a local `Dialect::gateway` on its old base URL; `llamafile` rides rig's llama.cpp dialect with `/v1` appended to `api_endpoint`. `provider::CompletionCallError` re-exposes the transport cause rig's `ProviderError::Http` hides, so `is_transient_error` still sees "connection refused"/"timed out". Tests pin each provider's wire (path, auth header, system-prompt placement) against a one-shot local listener (`test_support::capture_one_request`).
- **Persisted history is rig's serde format**: `agent_state.messages` stores rig `Message` JSON, so a rig upgrade can change it. rig 0.43 did (tagged assistant content, typed `CallId`, tool results carry `call` + `name`, reasoning sealed to its issuer); `legacy_history::upgrade` lifts 0.36-era history on every resume (idempotent), and `loop_dispatch::resumed_tool_result` pairs a resumed answer with its call from the history (`tool_call_id` = the call's wire id, or a 0.36 `fc_…` item id). Re-check this on every rig bump; a worker on the OLDER rig cannot read newer history.
- **Structured output**: `OutputDef::to_json_schema()` → JSON Schema injected into system prompt
- **Multi-turn** (Phase 7B+C): `tools: [{task: "..."}, {mcp: "..."}]` — task tools create async child jobs, MCP tools call external servers sync
- **Task-tool children must not be born terminal**: a tool result reaches the agent step only through normal step completion (`Settlement::propagate`'s `agent_tool` branch), so a child that is already terminal at creation (every root step skipped by `when`, or a server-dispatched root step that failed) can never deliver one. `agent_task_tool` calls `Settlement::agent_child_created`, which returns `Err(BornTerminal)` in that case (500 to the worker) instead of finalizing — the worker has not yet recorded the child id in `agent_state`, so propagation would mark the agent step ready or terminal out from under the still-running worker. `agent_child_created` first runs `reconcile` on the CHILD's own subtree, so a child that settles because a nested grandchild settled is caught by the same check. See § Settlement.
- **Agent registration barrier**: `Settlement::propagate`'s `agent_tool` branch returns `Ok(())` without touching the step when the parent step's `agent_state` is `None`, or when it parses but does not list this child in `pending_tool_calls`. The worker records pending child ids only AFTER the creation response, so anything earlier is unregistered — falling through to ordinary `mark_completed` would settle an agent step whose worker is still running. `agent_save_state` and `agent_suspend_step` (worker API) call `Settlement::agent_children_registered`, which replays `propagate` for every pending child that is already terminal right after persisting the state — that is what lifts the barrier. The child's terminal-handling claim was consumed by its own settlement, so the replay calls `propagate` directly, not `advance`.
- **ask_user**: `interactive: true` enables suspension → user approves → worker resumes
- **MCP client**: Servers spawn on worker (stdio/SSE). Config: `mcp_servers:` in workspace YAML
- **Max turns**: safety limit (default 25, max 100)
