# Templating and secrets

Secret redaction in logs and errors, value-free template errors, and the Tera 2 engine and render context. `CLAUDE.md` indexes this file. A `§ <Title>` reference names a `###` section in any file of `docs/internal/architecture/`.

### Secrets in logs

- **Secrets in logs**: wrap any field that can carry a rendered secret (action specs with `env`, resolved connection inputs, agent prompts/state, MCP server defs, step output, log lines) in `stroem_common::secret::Secret<T>` (re-export of the `redact` crate). `Debug` prints `[REDACTED T]`, reads go through `.expose_secret()`, `Serialize` needs `#[serde(serialize_with = "stroem_common::secret::serialize_opt_secret")]` so the wire format is unchanged. Never put a whole request/step struct into an `#[instrument]` span — use `skip(state, req)` / `skip_all` + explicit id fields. Regression tests: `test_claimed_step_debug_redacts_sensitive_fields` (worker), `test_worker_api_structs_debug_redacts_sensitive_fields` (server), `redaction::tests::redaction_debug_never_prints_secret_values` (`RedactionMemo` / `JobRedaction` hand-write `Debug` with counts only, like `Pinned`). `Secret<T>` only guards `Debug`; a secret **interpolated into a string** needs value scrubbing instead — `workspace_set::redact_secrets_in_str` (shared with the job-response redaction, `redaction::redact_str`) does **span-union masking**: it finds every occurrence of every secret value in the original text (overlapping occurrences included), merges intersecting or adjacent spans, and replaces each merged span with `••••••` — safe against one secret being a prefix/substring of another, or two secrets' occurrences crossing, which naive sequential replacement is not. **Template errors are value-free by construction** (spec `docs/superpowers/specs/2026-10-06-tera-2-upgrade-design.md` § 3.2): every Tera error is converted at the `stroem-common` boundary into `stroem_common::template_error::TemplateError` — a fixed category + position + detail drawn only from closed sets (type names, registered filter names, `TERA1_BUILTIN_NAMES`); Tera's own text, a value, a variable name or the template line is never copied. Tera's full text is reachable only through `TemplateError::raw_detail()` (with `vals` stderr), called solely by `stroem-cli` (`local/error_report.rs`, the `stroem run` / `stroem validate` printers); `stroem-common/tests/raw_detail_guard.rs` fails the build if any crate other than stroem-cli calls it, except the allow-listed test helpers (`stroem-common/src/template_error.rs` test fn, `stroem-server/src/test_support.rs`, `stroem-server/tests/common/tera_fixtures.rs`). Post-render errors (an error ABOUT a rendered value, after rendering succeeded) name the INPUT FIELD and a type, never the value or a part of it: connection resolution returns a value-free `ConnectionRefError` that the caller replaces with ``Input field 'db': <kind>`` (`check_connection_values` takes a label, not a connection name); `for_each` errors describe shape only. No `format!`/`bail!`/`context` in `template.rs`, `validation.rs`, `rendering.rs`, `cascade.rs`, `dispatch.rs`, `job_creator.rs` may interpolate a variable holding a rendered value. **Render-path table rule (spec § 3.4):** any NEW path that renders a template and reports the error must be added to that table and be value-free. Defence in depth stays: every claim-time render failure goes through `fail_claimed_step`, which scrubs before the message is logged to the job, persisted to `job_step.error_message`/`retry_history`, or returned in the 422 body; hook-input (`settlement/hooks.rs`) and event-source env (`event_source.rs`) render failures are scrubbed too. Any NEW path that persists or returns a rendered-template error must scrub the same way. Scrubbing guards SAME-workspace and server-log text always, and cross-workspace `type: task` text that carries no owner value (the caller's own input, or a structural error like a missing task). An owner-side render error — one that actually renders the OWNER workspace's own config — is withheld entirely (a fixed, value-free message) instead, once the step crosses that ownership boundary, because a filter chain can wrap a value in unboundedly many representations no finite scrub matches. Origin, not just which workspace is involved, decides withholding — see § Cross-Workspace References, `settlement/dispatch.rs::handle_task_steps_pass`. The same withholding applies at CLAIM for a step whose action owner ≠ `job.workspace` (live cross-workspace or ref'd, spec 2026-10-02 § 7.2): an `ActionDefault`-bucket `template::ProvenanceError` from `prepare_step_action_input` (owner defaults merge + owner connection pass, tagged inside `prepare_action_input_roles`) and ANY `render_action_spec` / `render_image` error (call-site origin — over-withholds a caller value in the body) are persisted, logged to the job and returned in the 422 as `rendering action '{name}' of workspace '{owner}' failed; details withheld` (`web/worker_api/rendering.rs::{withheld_owner_error, is_owner_side_prepare_error}`). Visible after scrubbing: the caller's step `input:`, a `Caller`-bucket error, pin errors, the unloaded-owner bail, and agent prompts (`Scope::AgentPrompt` renders in the caller's context). An own-workspace ref crosses no boundary. Claim-time scrubbing uses `claim_redaction_values` (live set + `pin_redaction_values` of every pin the claim loaded); a NEW claim-failure site must pass a `ClaimFailure` and choose `withheld` by origin. Redaction is strings-only; numbers, booleans and nulls are never masked (spec 2026-10-06-json-input-type D7). `stroem validate` warns about secrets written as YAML numbers.

### Tera Templating
- **Tera 2** (upgrade guide `docs/src/content/docs/operations/upgrade-tera-2.md`, spec `docs/superpowers/specs/2026-10-06-tera-2-upgrade-design.md`). One engine in `stroem-common`: `tera_engine.rs` (shared compile path for render AND `check_template_syntax`; registers `vals`, `json_encode`, the C3 ports), `tera_compat.rs` (Tera 1 behaviour kept), `template_error.rs` (`TemplateError`, see § Secrets in logs). Templates render on the server and in the CLI, never on workers — all server replicas must run the same Tera.
- **Kept from Tera 1**: C1 `default` also replaces `null`; C2 `state`/`global_state` are `null` (not absent) without a snapshot (`render_context::build`); C3 ported `as_str`, `trim_start_matches`/`trim_end_matches`, `linebreaksbr`, `map`, `filter`, `concat`, `slice`, `date`, `now`, `indent` (`prefix=`/`first=`/`blank=`, also `width=`/`indentation=`), `unique` (case-insensitive default, `case_sensitive=`, `attribute=`); C4 `evaluate_condition` is false for empty/`false`/`null`/`none`/`[]`/`{}`/numeric zero. Not restored: `urlencode(_strict)`, `slugify`, `filesizeformat`, `striptags`, `addslashes`, `get_env`, `spaceless`, `is matching`, `get_random` (named in `TERA1_BUILTIN_NAMES` → "not available in Tera 2" message).
- **Reserved step names**: `render_context::TERA_KEYWORDS` (Tera 2's 16 `RESERVED_NAMES` — `true`/`True`, `false`/`False`, `none`/`None`, `null`, `loop`, `self`, `and`, `or`, `not`, `is`, `in`, `continue`, `break` — plus `if`, `else`) are recorded as collisions and logged `[render] step '…' is a Tera keyword and cannot be referenced in templates`; not rejected at load.
- Unknown filters/tests/functions fail at parse time; `stroem validate` checks `when`, `for_each` and agent prompts via `check_template_syntax`.
- Step names with hyphens (e.g., `say-hello`) are sanitized to underscores (`say_hello`) in the template context because Tera interprets hyphens as subtraction.
- Workflow YAML must use underscored names in template references: `{{ say_hello.output.greeting }}`, not `{{ say-hello.output.greeting }}`.
- **Job metadata**: `{{ job.revision }}` (workspace revision pinned at job creation) is available in all template contexts — step inputs, `when` conditions, action bodies (script/cmd/env/args/image/manifest), agent prompts, approval messages. Always inserted (null → renders as `""` for pre-migration jobs). Hooks get the same value as `hook.revision` (both `HookContext` and `SuspendedHookContext`). `{{ job.ref }}` (`render_context::job_context(revision, git_ref)`) is a pinned job's ref as written, `null` (renders `""`) otherwise; `{{ job.revision }}` of a pinned job is its commit. Hooks get `hook.ref` (`HookContext.git_ref` / `SuspendedHookContext.git_ref`, serialised as `ref`).
- **`json` input fields** (spec `docs/superpowers/specs/2026-10-06-json-input-type-design.md`): `stroem_common::json_field` owns the rule — literal / exactly one `{{ expr }}` (native value via the `{% set __stroem_v = … %}…json_encode` wrapper, undefined top-level variables still error) / anything else an error. `template::render_input_typed` is the schema-aware renderer (non-`json` fields byte-for-byte `render_input_map`); `merge_defaults` / `merge_action_defaults` branch on `JSON_TYPE`. Claim reads the schema (json classification, defaults, connection-typed fields) from the step's persisted `action_spec.input` (`rendering::step_input_schema`; unreadable → fixed claim failure). Wrapper errors keep their category and get positions mapped back — never a second render. Re-run: `replay_fields` (typed `ReplayFieldsError` → 400) and every re-run needs the source's own task.
- **Single owner**: `crates/stroem-server/src/render_context.rs::build` builds the context for EVERY template field (S1 step input, S2/S3 action body + image, S4 agent prompts, S5 when/for_each, S6 task-step input + approval message). `Scope` is the only thing it matches on (which `input`, whose `secret`); `Scope::StepRef` and `Scope::TaskActionRef` (templated refs) carry no `secret`; `render_context::webhook_ref` is the second constructor (webhook input only); everything else — insertion order `input, secret, state, global_state, job, steps, each`, four statuses with masked output, loop-instance rows skipped — is one rule. `RenderContext` is opaque: never patch a variable into `as_value()`'s map after the fact; add it to `build`. Reserved step names are `FRAMEWORK_KEYS`; collisions are recorded on the context and logged. Snapshots for `state`/`global_state` are resolved once per entry by `render_context::latest_snapshots` (pool-only, migration 047's `state_json` column) in `Settlement::advance`, `dispatch::init` and `claim_job`, and threaded down as `&Snapshots` — `cascade::run` stays pure. `Snapshots.files` (the job's input files under the entry's root) is set by the same three entries after `latest_snapshots`, which always returns it empty — § File Inputs. Spec: `docs/superpowers/specs/2026-09-11-render-context-owner-design.md`.
